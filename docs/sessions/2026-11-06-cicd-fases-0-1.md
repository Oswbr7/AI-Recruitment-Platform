# Sesión 2026-11-06 — CI/CD Fases 0 y 1: CI con path filters + publicación de imágenes a GHCR

> **Tipo**: Infraestructura de pipelines (GitHub Actions)
> **Alcance**: Fase 0 (CI mejorado) + Fase 1 (CD de imágenes), según el plan acordado (destino final: Kubernetes; disparo: push→staging, tag→prod; sin infraestructura aún)
> **Estado al cierre**: ✅ Workflows escritos y YAML validado localmente (js-yaml + `docker compose config`). ⚠️ **Pendiente validación en GitHub**: el primer push con estos workflows confirmará el comportamiento real en runners (caches GHA, path filter, push a GHCR).
> **No requiere infraestructura**: GHCR usa `GITHUB_TOKEN` del propio workflow.

---

## 1. Contexto y problema

El CI heredado validaba solo el build del backend. No había validación de frontend, los Dockerfiles solo se probaban a mano con `docker compose up`, y no existía ninguna publicación de artefactos desplegables. El plan acordado en la sesión previa estableció 4 fases; esta sesión ejecuta las dos primeras (independientes del destino final de despliegue).

## 2. Decisiones tomadas (y por qué)

| Decisión | Alternativa rechazada | Razón |
|---|---|---|
| Path filtering por job (`dorny/paths-filter`) | `paths:` nativo por workflow | El filtro nativo aplica al workflow entero; el propósito era no compilar lo que no cambió **por job** (la lección de `Notas.md`) |
| Jobs: `changes` → `backend-validation` / `frontend-validation` / `docker-validation` | Un solo job monolítico | Paralelismo + feedback específico por área; el job `docker` solo corre si cambió src, Dockerfiles o compose |
| Docker validation con `build-push-action` `push: false` + cache GHA por imagen | `docker build` a pelo | El cache GHA (`type=gha,scope=<imagen>`) hace que rebuilds en PRs sean baratas; valida los Dockerfiles en cada cambio de código sin publicar nada |
| Imágenes a **GHCR** | Docker Hub | Sin credenciales extra (`permissions: packages: write` + `GITHUB_TOKEN`); imágenes junto al código |
| Tags **SHA + latest** | Solo `latest` | Despliegue reproducible y rollback = re-deploy del SHA anterior; `latest` para referencia cómoda |
| Frontend: ARGs en Dockerfile con defaults de dev | Dejar el Dockerfile como estaba | Sin ARGs la imagen publicada quemaría URLs vacías (el `.env` no se versiona). Los defaults (`localhost:500x`) preservan la paridad exacta con el compose local; el CD sobrescribe con `--build-arg` desde variables del repo |
| Build-args del frontend desde **repo variables** (`vars.*`) con fallback a defaults | Secrets | Las URLs de API no son secretas; las configuration variables son visibles y auditable, los secrets no |
| Scope de cache separado CI/CD (`ci-<imagen>`) | Compartir scope | Evita que el cache de validación (PRs) compita con el de publicación (main) |

## 3. Cambios realizados

### 3.1 `.github/workflows/ci.yml` (reescrito — Fase 0)

```
changes (dorny/paths-filter) ─┬─► backend-validation   (slnx restore+build, cache dotnet)
                              ├─► frontend-validation  (npm ci cacheado + oxlint + tsc/vite build)
                              └─► docker-validation    (matrix 6 imágenes, build sin push,
                                                        cache GHA + validación compose config)
```

- Filtros: `backend` (services/, building-blocks/, props, slnx, global.json), `frontend` (frontend/**), `docker` (Dockerfiles, .dockerignore, nginx.conf, Infraestructure/docker/).
- El job docker corre si cambió **cualquier src** (las imágenes empaquetan el código).
- Paso nuevo: `docker compose --env-file .env.example ... config -q` valida la sintaxis del compose en cada corrida (verificado localmente).
- Se conserva el `TODO` de tests y el `concurrency` con cancel-in-progress.

### 3.2 `.github/workflows/cd.yml` (nuevo — Fase 1)

- Trigger: push a `main` (staging llegará en la Fase 3 con environments; por ahora solo publica).
- Matriz de 6 imágenes (contextos según compose: raíz para servicios, `frontend/web-app` para el frontend).
- `Resolve Image Prefix`: lowercases el owner (GHCR lo exige) → `ghcr.io/<owner>/ai-recruitment/<imagen>`.
- Login a GHCR con `GITHUB_TOKEN`; push con tags `:<sha>` y `:latest`.
- Build-args `VITE_*` para el frontend desde `vars.*` del repo con fallback a los defaults del Dockerfile.
- Mismo scope de cache que CI: la primera corrida de CD reutiliza las capas ya cacheadas en CI.

### 3.3 `frontend/web-app/Dockerfile`

- 5 `ARG`/`ENV` `VITE_*` con defaults `http://localhost:500x/api` (idénticos al entorno local actual).
- Vite lee `process.env.VITE_*` con prioridad sobre `.env`, así que el comportamiento local no cambia y el CD puede parametrizar.

## 5. Descubrimientos para la siguiente sesión

1. **Primera corrida en GH Actions**: revisar que el path filter detecte bien los cambios (especialmente en push a main, donde compara contra el commit anterior) y que el push a GHCR funcione con el owner en minúscula.
2. **Configurar repo variables** cuando se definan los dominios del entorno (Settings → Actions → Variables: `VITE_API_URL`, etc.). Hasta entonces, la imagen de frontend publicada lleva URLs de localhost — **no desplegable**, como se documentó.
3. **Fase 2 (K8s) prerequisitos intactos**: manifiestos + Kustomize overlays, Secret JWT, Job de migraciones, decisión gateway. La imagen del frontend quedará desplegable cuando el gateway defina una URL única (probablemente un solo `VITE_API_URL` apuntando al ingress).
4. **Fase 3**: `deploy.yml` con environments `staging` (push a main) y `production` (tag `v*` + approval) — necesitará secrets `KUBECONFIG_*` cuando exista el clúster (kind/k3d primero).
5. El paquete `Microsoft.Extensions.Options.*` redundante (warning NU1510) sigue pendiente del Bloque 1 — candidate a limpieza rápida.

## 6. Qué NO se hizo (y por qué)

- **No se despliega nada** — es la Fase 3, bloqueada por manifiestos K8s (Fase 2) y por kubeconfig/infraestructura (que el usuario confirmó que aún no existe).
- **No se agregó el environment `staging` al CD** — sin clúster no hay nada que desplegar; la publicación de imágenes en push a main ya deja artefactos versionados por SHA listos para ese momento.
- **No se tocaron los Dockerfiles de los servicios** — no necesitan ARGs (las URLs y el JWT llegan por variables de entorno en runtime, no en build).
- **No se agregó análisis de imágenes (Trivy/Snyk)** — candidato natural para endurecer el pipeline después de la primera corrida exitosa.
