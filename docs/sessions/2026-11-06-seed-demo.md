# Sesión 2026-11-06 — Seed de datos de demostración (`tools/SeedDemo`)

> **Tipo**: Feature de aplicación (herramienta)
> **Estado al cierre**: ✅ Compila solo y dentro de la slnx (0 errores). ⚠️ Ejecución real pendiente de Docker (requiere el stack arriba); los contratos fueron verificados contra el código de los endpoints y de los API clients del frontend.

---

## 1. Contexto y problema

La plataforma funcionaba pero vacía: probar el dashboard, el matching o el admin de usuarios requería crear datos a mano servicio por servicio. Se decidió una app de seed **a través de las APIs reales** (no seed EF ni inserts directos) porque además de poblar datos, ejerce la superficie completa: registro, login, autorización por roles, creaciones y transiciones de estado.

## 2. Decisiones tomadas (y por qué)

| Decisión | Alternativa | Razón |
|---|---|---|
| **App de consola .NET** (`tools/SeedDemo`, sin paquetes NuGet) | Script bash/curl, seed EF (`HasData`), inserts SQL | Cross-platform real; usa HttpClient + System.Text.Json del BCL; entra en CI vía slnx; no toca migraciones ni acopla a esquemas |
| **Por las APIs** (HTTP) | Acceso directo a las 5 bases de datos | Valida la API real end-to-end (auth, envelopes, autorización); funciona igual contra compose o k8s solo cambiando env vars |
| **Idempotencia por clave natural** (email de usuario/candidato, nombre de empresa, título de vacante/entrevista) | Borrar y recrear | Re-ejecutable sin miedo; no destruye datos que alguien haya editado encima del demo |
| **Credenciales por env vars con defaults de desarrollo** | Hardcode sin escape | `ADMIN_EMAIL`/`ADMIN_PASSWORD` sobrescribibles; los defaults (`admin@demo.local` / `Demo123!`) son de desarrollo y así se documentan |
| **El seed ejerce el flujo de roles** | Crear el recruiter con UPDATE directo | Registra el segundo usuario y lo promueve con `PATCH /api/users/{id}/role` usando el token Admin — demuestra el feature de la sesión anterior de punta a punta |
| **Datos pensados para el matching** | Datos aleatorios | Los 6 candidatos tienen perfiles deliberadamente distintos (ubicación, años, salario, stage, keywords) para que el ranking del matching muestre diferencias visibles |
| **Feedback seed incluido** | Solo entrevistas | Una entrevista se agenda en el pasado, se completa y recibe feedback `StrongHire` — deja datos para el detalle de entrevista |

## 3. Cambios realizados

- **`tools/SeedDemo/`** (nuevo): csproj (net10.0, exe, cero paquetes) + `Program.cs` (~380 líneas, procedural con helpers locales):
  - `SeedConfig` — env vars con defaults de compose local (puertos 5000-5004).
  - Marcadores de consola `[ok]` / `[skip]` con resumen final (credenciales de demo).
  - Flujo: usuarios (admin primer-registro + recruiter promovido) → 3 empresas → 4 vacantes (creadas **y publicadas**) → 6 candidatos → 4 entrevistas → 1 completada + feedback.
  - Manejo de errores con mensaje accionable ("verifica que el stack esté arriba").
- **`AIRecruitmentPlatform.slnx`**: carpeta `/tools/` con SeedDemo → el CI lo compila.
- **`README.md`**: paso 3 opcional del quickstart.
- **`architecture.md`**: nota del seed en el gap de roles (el primer Admin de un deploy con seed debería venir de aquí).

## 5. Descubrimientos para la siguiente sesión

1. **`GET /api/jobs` no paginado** facilitó el chequeo de idempotencia de vacantes (array plano) pero confirma la deuda conocida — al paginarlo, el seed debe migrar al chequeo por `search`.
2. El seed asume que el **primer registro es Admin** — si la base ya tiene usuarios (p.ej. uno creado a mano), el admin del seed nace Candidate y el `PATCH role` fallaría con 403. Mitigación documentada: el seed imprime el error del backend; endurecimiento futuro: comprobar el rol tras el login y auto-promover solo si ya hay otro Admin.
3. Evolución natural documentada: Job de Kubernetes `seed-demo` que corra `SeedDemo` contra el cluster (misma imagen multi-stage, `dotnet run` o self-contained), reutilizando las env vars de los Services.

## 6. Qué NO se hizo (y por qué)

- **No se agregaron notas de candidatos ni contactos de empresa** — mismos endpoints sub-recurso, mecánica idéntica; extensión trivial registrada.
- **No se hizo el Job de k8s para el seed** — sin cluster aún; queda como evolución cuando el smoke test en kind exista.
- **No se ejecutó el seed** — requiere los servicios corriendo (Docker); es parte del smoke test.
- **No se versionó ninguna credencial real** — las del seed son de desarrollo y se documentan como tales.
